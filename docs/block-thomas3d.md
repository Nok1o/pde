# Матричная прогонка для 3D-теплопроводности — issue #26

Метод `block` решает замороженную линейную систему внутри Пикара блочной
прогонкой по z-плоскостям. Он использует тот же `HeatOperator3D`, что и
направленные прогонки `lod`: одинаковы физический шаг неявного Эйлера,
проводимость, правая часть, граничные данные и проверки нелинейной сходимости.
Меняется внутренний линейный решатель. Полный временной расчёт по-прежнему
начинается с известного начального поля и использует вычисленный предыдущий
слой; аналитическое решение служит только внешней проверкой.

В интерфейсе **Квазилинейная теплопроводность → 3D** можно выбрать оба метода.
Общая постановка, области запроса и протокол исследования описаны в
[heat3d.md](heat3d.md), соглашения об операторе — в
[heat3d-contract.md](heat3d-contract.md).

## Система по плоскостям

Пусть `n` — число интервалов по оси, `s=n+1` — число узлов. Вектор `u_z`
содержит всю плоскость `[y,x]` при фиксированном z, включая известные
граничные узлы; x меняется быстрее. Длина вектора `m=s²`.
Семиточечная система принимает блочно-трёхдиагональный вид:

$$L_z u_{z-1}+B_z u_z+U_z u_{z+1}=b_z,\qquad z=0,\ldots,n.$$

`B_z` содержит полную диагональ и связи по x/y. Матрицы `L_z` и `U_z`
диагональные: они связывают узлы с теми же x/y в соседних z-плоскостях.
Элементы этих матриц равны **минус** соответствующим неотрицательным весам
оператора; `L_0=0`, `U_n=0`. Вес z− берётся из своей строки и не заменяется
весом z+ соседней строки. Поэтому симметрия матрицы не требуется.

В фиксированном узле сохранена единичная строка. Связи к известным узлам уже
исключены общим оператором, а их вклад уже включён в `b_z`.
Блочная прогонка не добавляет граничные значения в правую часть повторно.

## Прямой и обратный ход

Обозначим через `solve(D, r)` решение системы с матрицей D и одной либо
несколькими правыми частями r. Подготавливаются блоки Шура:

$$D_0=B_0,\qquad G_0=\operatorname{solve}(D_0,U_0),$$
$$D_z=B_z-L_zG_{z-1},\qquad
G_z=\operatorname{solve}(D_z,U_z).$$

Последний блок `D_n` тоже факторизуется, но `G_n` не нужен. Каждый `D_z`
разлагается в LU с выбором ведущего элемента. В коде используются
`scipy.linalg.lu_factor` и `lu_solve`; явная обратная матрица не вычисляется.
Прогонка работает с отдельными плотными блоками и не вызывает разреженную
факторизацию полной системы.

Для конкретной правой части выполняется прямой ход:

$$h_0=\operatorname{solve}(D_0,b_0),\qquad
h_z=\operatorname{solve}(D_z,b_z-L_zh_{z-1}).$$

Затем обратный ход:

$$u_n=h_n,\qquad u_z=h_z-G_zu_{z+1},\quad z=n-1,\ldots,0.$$

После полного решения проверяется настоящая невязка общего оператора
`||Au−b||∞/||b||∞` на свободных узлах. Фиксированные значения восстанавливаются
точно. При нулевой норме правой части отношение равно нулю только при нулевой
невязке, иначе бесконечности. Один законченный прямой и обратный ход считается
одной внутренней итерацией. Если начальное поле уже удовлетворяет допуску,
решатель завершается с нулём проходов и без новой факторизации.

Линейное решение затем проходит обычную релаксацию Пикара. Приём физического
слоя требует проверки исходной нелинейной невязки с заново вычисленной
проводимостью и относительного изменения поля. Прямое решение замороженной
системы само по себе не завершает нелинейную задачу.

## Когда можно использовать факторы повторно

Один экземпляр `BlockThomasSolver3D` хранит факторы только **одной матрицы**:
LU блоков `D_z` и матрицы `G_z`. Для следующего вызова проверяются неизменяемые
массивы `diagonal` и `weights`: сначала идентичность объектов, затем при
необходимости точное равенство элементов. Приближённого сравнения и допуска
на изменение коэффициентов нет. При смене матрицы прежние факторы удаляются
до подготовки новых; незавершённая факторизация не попадает в кэш.

Изменение одной правой части сохраняет возможность повторного использования.
Это относится и к `operator.with_rhs(...)`: переданная правая часть уже
скорректирована, в том числе в фиксированных строках. При точном совпадении
новых массивов кэш начинает ссылаться на текущий снимок оператора, освобождая
ссылки на прежние массивы.

При `alpha=0` и одинаковом фактическом `dt` матрица может оставаться постоянной
между итерациями и физическими слоями, даже если правая часть меняется.
Изменение `dt`, включая укороченный последний шаг, меняет временную массу
`1/dt` и требует новых факторов. При `alpha>0` изменение проводимости также
обычно меняет матрицу. Решение о повторе всегда основано на точном сравнении
массивов, а не только на параметрах `alpha` и номинальном `dt`.
Каждый отдельный полный запуск, включая повтор исследования, создаёт свой кэш
и оплачивает его подготовку.

## Размеры, память и стоимость

Реализация ограничена `n≤16`. Хотя исходный шаблон разреженный, блоки Шура
становятся плотными. Для `s=n+1` плоскостей размера `m=s²` подготовка LU и
`G_z` имеет порядок `O(s·m³)=O(n⁷)`, хранение факторов — `O(s·m²)=O(n⁵)`.
Решение с готовыми факторами для новой правой части требует `O(s·m²)=O(n⁵)`
операций. Эти оценки объясняют ограничение размера; они не устанавливают
выигрыш во времени относительно ЛОМ.

`block_workspace_bytes(n)` оценивает численные буферы до выделения плотных
массивов:

$$8\big((2s+2)m^2+24s^3+sm\big)\ \text{байт}.$$

В оценку включены s LU-блоков, s−1 матриц `G_z`, запас на три временных плотных
блока, индексы перестановок и полные поля для правой части, кандидатов,
невязок, временных массивов и кратковременно удерживаемой прежней матрицы.
Для `n=16` это **25 036 648 байт** только на блочный решатель. Временной
решатель дополнительно учитывает общий оператор, физические поля, сетку
времени и историю. Лимит `--max-workspace-bytes` относится к общей оценке;
по умолчанию он равен 256 MiB.

Ограничение n и бюджет проверяются до копирования начального приближения
и сборки блоков. Кэш другой размерности освобождается до выделения полей
новой сетки. `workspace_bytes` — оценка рабочих массивов, а не измеренный RSS
процесса; без отдельного измерения `peak_rss_bytes` остаётся `null`.

Отказы возвращаются явно:

| Статус | Причина |
|---|---|
| `unsupported` | Размер превышает ограничение или вход не поддерживается |
| `memory_limit` | Оценка превышает бюджет либо выделение памяти не удалось |
| `nonfinite` | Начальное поле, промежуточные значения или невязка не конечны |
| `linear_limit` | Сингулярный блок либо невязка полного решения выше допуска |

При незавершённом прямом решении внутренний счётчик не увеличивается.
Слишком строгий допуск может дать `linear_limit` после полного прохода со
счётчиком 1. Последний кандидат сохраняется как диагностика, но не выдаётся
за решение в целевой момент.

## Что входит во время

Общее `seconds` включает подготовку, всю временную цепочку, Пикар,
линейные решения и проверки остановки. Прогрев JIT для ЛОМ, аналитический
и независимый ньютоновский эталоны, UI и экспорт учитываются отдельно.

| Поле | Что измеряется |
|---|---|
| `assembly_seconds` | Сборка плотных блоков и проверка совпадения матрицы |
| `factorization_seconds` | LU блоков Шура и подготовка `G_z` |
| `solve_seconds` | Подстановка правой части, обратный ход и линейные невязки |
| `factorizations` | Полностью подготовленные новые факторизации общей матрицы |
| `factor_reuses` | Использования уже готовых факторов |

У линейной попытки свои метрики: счётчики новых факторизаций и повторов
равны 0 или 1, а не накопленному значению экземпляра решателя. Слой и полный
запуск суммируют метрики попыток, включая затраты неудачных попыток.
`assembly_seconds` входит в `preparation_seconds`. Все времена из таблицы и
`preparation_seconds` уже входят в `seconds`; прибавлять их к общему времени
нельзя. Отдельные стадии помогают объяснить стоимость, но не заменяют
измерение всей цепочки до T.

## Воспроизводимый запуск

Сравнение одной и той же задачи обоими методами с независимым Ньютоном:

```sh
python -m pdelab.heat3d_cli run --methods lod block --case polynomial --n 8 --alpha .5 --dt .01 --T .02 --query field --newton --out runs/heat3d-block-run
```

Исследование времени достижения 1/5/10% с отдельными предварительными
и финальными сериями для каждого метода:

```sh
python -m pdelab.heat3d_cli study --methods lod block --n 8 --alpha .5 --dt .01 --T .02 --repeats 5 --seed 42 --out runs/heat3d-block-study
```

`--methods block` запускает только матричную прогонку; без `--methods`
сохраняется прежний выбор `lod`. Оба метода детерминированы: повторы измеряют
время, а изменение seed не меняет их решение. Исследование использует общий
протокол `fixed_candidate_independent_final_v1` и среднюю относительную
L2-ошибку отдельных запусков `mean_run_relative_l2_v1`.
Если цель не подтверждена, сохраняются фактическая ошибка, затраты и причина;
успешное завершение не предполагается заранее.

## Проверки и область применимости

`tests/test_heat3d_block.py` сравнивает решения с независимо собранной
CSR-системой, включая неодинаковые направленные веса, фиксированные строки,
исключение граничных вкладов и предельное `n=16`. Отдельно проверяются
скорректированная правая часть, точное повторное использование факторов,
смена матрицы и размера, отказы до выделения памяти, очистка незавершённого
кэша и реальная линейная невязка.

Физический 3D-режим пока поддерживает **условия 1 рода на всех шести гранях**.
Блочное ядро допускает несимметричный неизменяемый `HeatOperator3D`, но это
не означает готовой дискретизации условий 3 рода: её добавляет #27.
MC и контрольное приближение относятся к #28. Сравнительные измерения должны
учитывать всю временную цепочку и одинаковую точность; наличие прямого
линейного решателя само по себе не является утверждением о преимуществе.

## Измеренный результат

[Пилот n=4/8/16 с исходными данными](../benchmarks/results/heat3d-block/README.md)
сравнивает полную временную цепочку при одинаковых целях точности. В нём
матричная прогонка не обгоняет ЛОМ; сохранены затраты факторизации, повторного
использования и памяти, а также недостигнутые цели.
