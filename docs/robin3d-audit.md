## Проверенный оператор

`boundary.py: BoundaryOperator`, `boundary3d.py: BoundaryOperator3D` используют
узловые конечные объёмы. Уравнение старого режима: `Delta u=f`, граница
`du/dn + beta*u = r`, k=1. Внешняя нормаль на x0/y0/z0 отрицательная, на
x1/y1/z1 положительная; физический поток наружу равен `-du/dn=beta*u-r`.

Для неизвестного узла i с объёмом V и граничными площадями S:

`d_i u_i - sum_j a_ij u_j = -f_i + sum_faces (S/V)*r_face`,

`d_i = sum_j a_ij + sigma_i`, `sigma_i = sum_faces (S/V)*beta_face`.

На равномерной сетке внутренние веса равны `1/h²`. Отсутствующий наружный
сосед отражается во внутреннего: вес внутрь вдоль граничной нормали равен
`2/h²`. Для каждого инцидентного условия 3 рода `S/V=2/h`. Объёмы равны
h³, h³/2, h³/4 и h³/8 во внутренности, на грани, ребре и в углу; сумма
объёмов равна 1. На стыках вклады граней складываются. Если присутствует
условие 1 рода, оно фиксирует узел; разные значения 1 рода на стыке отвергаются.

Взвешенная сумма диффузионных вкладов по всем узлам без фиксированных значений
равна нулю: внутренние потоки попарно сокращаются. При всех гранях 3 рода
`sum(V*reaction*u)=sum(V*(-f+boundary_load))` — дискретный интегральный баланс.
Это проверено на произвольном поле, независимо от изготовленного решения.

## Проверенное правило MC

`P_ij=a_ij/d_i`, `reward_i=(-f_i+sum(S/V)*r)/d_i`,
`p_absorb_i=sigma_i/d_i`; `sum_j P_ij+p_absorb_i=1`.

Поглощение не задаётся постоянными 20%. Например, при n=4 и beta=1 для всех
граней в углу `sigma=24`, `sum(a)=96`, поэтому только **в этом** узле этого
случая получается 24/120=20%. На грани, при другом h или beta вероятность
другая, а внутри — ноль.

В `boundary_solvers3d.py: _walks` после выплаты reward выполняется проверка
поглощения, иначе выбирается одна из шести отражённых попыток. Условные веса
равны 1/6; две попытки у границы ведут к одному внутреннему соседу. Полученные
безусловные вероятности совпадают с P на гранях, рёбрах и в углах. При достижении
фиксированного узла выплачивается g и путь завершается. Прямой решатель и
направленные прогонки решают тот же стационарный оператор. Отдельный
матричный backend нелинейной временной задачи относится к #26.

## Проверочные данные

`stationary_snapshot` в `pdelab/boundary_audit3d.py` использует две функции #24:

- `u*=1+sin(pi*x)sin(pi*y)sin(pi*z)`;
- `u*=1+(x+2y+3z+xy+xz+yz+x²+y²+z²)/4`.

Это снимки при t=0. При alpha=0 проверочный тепловой источник F удовлетворяет
`F=u_t-Delta(u*)`; поэтому старому оператору передаётся **f=u_t-F**, а не F.
Граничные данные берутся при k=1 и beta=1 из того же точного решения.
Аналитическое поле хранится только экспериментом: backend получает
`BoundaryProblem3D(exact=None)`.

Варианты: все грани 1 рода; только y0 — 3 рода; все грани 3 рода.
Источник, производные и значения на всех шести гранях проверены независимыми
формулами. Для перекрёстного полинома дискретные уравнения и прямое решение
точны до округления. Для синусного снимка на сетках 8→16 проверен второй
порядок относительно аналитики для всех трёх вариантов.

## Измеренная серия

[Отчёт и таблицы](../benchmarks/results/pde27-stage1-n16/README.md),
[CSV всех целей](../benchmarks/results/pde27-stage1-n16/summary.csv),
[исходные попытки](../benchmarks/results/pde27-stage1-n16/attempts.json).

n=16, центр, R=5, root seed=20261125, цели 1/5/10%. Метрика
`mean_run_relative_l2_v1`, протокол `frozen_budget_holdout_v1`. Сначала
подбирается бюджет с фиксированным запасом (MC 0.5, ЛОМ 1.0), сохраняется
selection.json, затем запускается контроль. Контроль не используется для
повторного подбора. Его данные переиспользуются для нескольких целей только
при одном уже выбранном бюджете. Фактические seed backend — uint32,
явно полученные из SeedSequence; они сохраняются вместе с полными повторами.

Все 36 строк целей в этом пилоте подтверждены. При цели 1%:

- Все грани 1 рода: MC дороже ЛОМ для обеих функций.
- Одна грань 3 рода: MC дешевле ЛОМ в измеренных настройках обеих функций.
- Все грани 3 рода: MC дороже ЛОМ; относительно MC с 1 родом цена выросла
  примерно в 23.5 раза на синусе и в 4.4 раза на полиноме.

Это сравнение времени достижения порога при подобранных бюджетах. Оно включает
разницу в числе путей и не изолирует аппаратную цену одного отражения.
Времена миллисекундных расчётов чувствительны к фоновому состоянию компьютера;
стандартное отклонение сохранено. Вывода о всеобщем преимуществе метода нет.
На графиках присутствуют неподходящие пилотные бюджеты, а не только победители.

Исходники измеренного запуска сохранены в source.zip с SHA256 и признаком
dirty: runner был незакоммичен. Код отчёта форматирует сохранённые результаты
без нового вычисления и не входит во время решателя. RSS не измерялся;
оценка буферов явно отделена от пика процесса. n=32 и нецентральная точка
остаются расширением пилота #31. Старый backend при исключении не возвращает
частичные счётчики: адаптер сохраняет время и причину, а неизвестные пути и
переходы обозначает null. В этой реальной серии исключений не было; отказной
случай проверен тестом.

Воспроизведение из виртуального окружения:

```sh
python -m pdelab.boundary_audit3d --n 16 --repeats 5 --seed 20261125 --seconds 120 --out runs/pde27-stage1
python -m pdelab.boundary_audit_report runs/pde27-stage1
python -m pytest tests/test_boundary_audit3d.py tests/test_boundary3d.py tests/test_boundary_solvers3d.py tests/test_measurement_protocol.py -q
```

Результаты выводятся в новую папку; существующие попытки не перезаписываются.
Время включает подготовку входных полей и работу backend. JIT, внешняя
аналитическая проверка и экспорт исключены; их границы указаны в protocol.json.

## Следующий отдельно принимаемый этап

Перенос на k(u), физическое время и оператор #25. Его строка содержит
`1/dt`, проводимости на рёбрах и физический теплообмен `k*du/dn+beta*u=r`.
Поэтому нельзя копировать стационарные вероятности или просто передать r в
нормированное условие Пуассона. Коэффициенты нужно вывести заново, проверить
баланс и изготовленные решения, связать с тем же оператором для #26/#28,
подключить поддержанные случаи к CLI, сравнению, исследованию, UI и экспорту.
Для окончательной приёмки #27 нужны эти проверки и второй пакет измерений.

## Формат аудита и преобразование

Агрегированный пакет имеет собственную версию `boundary_audit_v1`: общие
сведения находятся в protocol.json, отдельные серии — в attempts.json,
сводки целей — в results.json/summary.csv. В серии trials содержит повторы
с известными счётчиками; failures сохраняет исключения старого backend с
неизвестными walks/transitions=null. Это не канонический measurement_v1,
в котором каждая серия содержит собственный обязательный metadata.

`canonical_series_files(attempt, protocol, target_pct=...)` — явный адаптер
в measurement_v1. Он переносит commit/окружение, Q/эталон, конфигурацию,
бюджет, границу таймера и память в metadata, сохраняет исходную summary и
диагностику в diagnostics, передаёт все trials общему export_series и явно
задаёт stochastic по методу. Seed, фаза и нумерация повторов не меняются.
Если failures непуст, преобразование отклоняется: обязательные целочисленные
счётчики Trial пока не представляют неизвестную работу. Такая серия остаётся
в boundary_audit_v1 со временем и причинами; подставлять нули или выбрасывать
неудачные повторы запрещено.

В первом опубликованном пакете серии ошибочно содержали метку measurement_v1.
Миграция меняет только метки схемы и добавляет версию агрегированного пакета;
format-migration.json сохраняет исходные SHA256 и описание изменений.
Измеренные значения, времена, seed, статусы и source.zip не менялись.
Архивный код сохраняет исходную, ошибочную метку как факт происхождения.
Перегенерированный README использует фактические функции, R, Q и статусы
сводок, включая not_reached, incomplete и not_selected.
