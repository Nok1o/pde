# #33: хранение данных временной задачи

В 3D-решателе уже хранятся только необходимые полные поля предыдущего слоя
и текущей итерации. Перенос старой идеи «не хранить все временные поля» сам
по себе здесь ничего не сокращает. Изменение касается **скалярной истории
итераций**: она растёт по мере расчёта и на длинной цепочке может занимать
больше памяти, чем рабочие поля малой сетки.

## Два режима диагностической истории

`HeatSettings3D.history_mode` принимает:

- `full` — прежнее поведение, все записи внешних итераций; это значение
  по умолчанию.
- `layers` — одна последняя запись на каждый начатый физический слой.
  Промежуточная запись заменяется следующей, а счётчики работы складываются.

Пример Python API:

```python
from pdelab.heat3d_problem import make_heat_problem3d
from pdelab.heat3d_solver import HeatSettings3D, solve_heat3d

problem = make_heat_problem3d("polynomial", n=8, alpha=0.5)
result = solve_heat3d(
    problem,
    dt=0.002,
    T=0.02,
    settings=HeatSettings3D(history_mode="layers"),
)
```

Результат сохраняет `history_mode` и `history_records_discarded` — число
удалённых промежуточных записей. У каждой строки режима `layers` есть
`records_discarded` для данного слоя. Суммарные пути, завершённые пути,
перемещения, пути независимых проверок и грубые итерации учитывают **все**
попытки слоя. Невязки, изменение поля, причина отказа и seed в этой строке
относятся только к последней записанной попытке. Если последняя попытка не
содержала независимой проверки, её отсутствующий seed или невязка не
подменяются данными более ранней проверки.

Промежуточный график сходимости внутри слоя восстановить из `layers` нельзя.
Режим не восстанавливает данные повторным решением и не пишет их на диск;
расходов на такое восстановление или ввод/вывод нет. Исторические полные
поля не сохранялись и в `full`, поэтому произвольные прошлые пространственные
срезы не появляются ни в одном режиме. Поле в запрошенный момент T и
последний неудачный кандидат сохраняются как прежде.

## Какие данные остаются обязательными

| Данные | Для чего нужны | Срок хранения |
|---|---|---|
| Предыдущее полное поле | Правая часть следующего неявного слоя | До принятия следующего слоя |
| Текущий кандидат и замороженный оператор | Пикар, истинная невязка, линейное решение | Текущая итерация/слой |
| Грубое поле и поправка | Контрольное приближение MC | Текущая оценка поля |
| Активные частицы | Незавершённые траектории | Текущая группа путей |
| Множество использованных seed | Не допускать повтор потока при 32-битной коллизии | Весь полный запуск |
| Итерационные скаляры | Диагностика/графики/экспорт | По выбранному режиму истории |
| Эталон | Только внешняя оценка ошибки | Вне рабочего решателя |

Множество seed и сами целые seed не удаляются при сжатии истории. Их память
учитывается отдельно от диагностических строк; общие ссылки на seed не
считаются второй раз. Поэтому `layers` не делает память стохастического
расчёта строго постоянной по числу оценок. И в нём остаются все необходимые
поля, временная сетка и реестр seed.

Численные формулы, частота обновления коэффициентов, критерии остановки,
порядок случайных выборов и бюджеты путей не меняются. При одинаковом seed
и достаточных лимитах решения и счётчики совпадают побитово. При более
тесном лимите памяти полный режим может остановиться раньше, поскольку
сохраняет больше диагностики. Лимит времени относится к фактической работе:
другая стоимость хранения также может повлиять на остановку по времени.

## Исходный профиль

Входной профиль проведён на `b81c243` до изменения хранения, Python 3.13.14,
NumPy 2.5.4, Numba 0.68.0, macOS arm64. Полином, n=4, α=0.5, T=0.1,
допуски Пикара 10⁻⁷, ЛОМ, одна точка в центре. Прогрев JIT и создание задачи
предшествуют `tracemalloc`; время здесь **не измерялось**.

| Слоёв | Строк истории | Оценка истории, байт | Оценка всех буферов, байт | Пик tracemalloc, байт |
|---:|---:|---:|---:|---:|
| 20 | 80 | 67752 | 108320 | 163905 |
| 200 | 600 | 505032 | 549920 | 483473 |
| 1000 | 2000 | 1664184 | 1728272 | 1259465 |

[Исходные данные](../benchmarks/results/heat3d-storage-gate.json).
Оценка через `getsizeof` консервативна и может повторно учитывать общие
скалярные значения; `tracemalloc` отслеживает поддержанные выделения, а не
весь RSS процесса. Эти величины не обязаны совпадать. Профиль доказывает
наличие растущей диагностики, но не является итоговым сравнением full/layers.

Воспроизведение исходного профиля на указанной версии:

```python
import tracemalloc
from sys import getsizeof

from pdelab.heat3d_linear import warmup_lines3d
from pdelab.heat3d_problem import make_heat_problem3d
from pdelab.heat3d_solver import HeatSettings3D, solve_heat3d

warmup_lines3d()
problem = make_heat_problem3d("polynomial", 4, 0.5)
for layers in (20, 200, 1000):
    tracemalloc.start()
    result = solve_heat3d(
        problem,
        dt=0.1 / layers,
        T=0.1,
        settings=HeatSettings3D(max_seconds=60),
    )
    retained, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    history_bytes = getsizeof(result.history) + sum(
        getsizeof(row) + sum(getsizeof(value) for value in row.values())
        for row in result.history
    )
    print(layers, result.status, len(result.history), history_bytes, peak)
```

## Проверки и план итоговых измерений

`tests/test_heat3d_history.py` сравнивает все шесть методов и независимый
Ньютон с полной историей, проверяет укороченный последний слой, несколько
seed, отказы независимых MC-проверок, агрегаты работы и ограничение памяти.
Побитовое совпадение при одинаковых потоках здесь сильнее сравнения
средних двух независимых шумных серий: изменяется только хранение диагностики.

Для финального согласованного окна подготовлены планы существующего runner
#31, без второго механизма исследования:

```sh
python -m benchmarks.heat3d_pilot --plan benchmarks/heat3d-storage.json --out runs/heat3d-storage
python -m benchmarks.heat3d_pilot --plan benchmarks/heat3d-storage-long.json --out runs/heat3d-storage-long
```

Первый план: все шесть методов, n=6/12, 4/16 физических слоёв, точка/поле,
условия 1 и 3 рода. Второй: длинные истории ЛОМ на n=4/8, 200/1000 слоёв,
точка/поле. У каждого метода есть отдельные варианты `full` и `layers` с
одинаковыми seed и бюджетами; R=3, один фиксированный кандидат допуска или
числа путей. Runner сохраняет полную стоимость, ошибки, отказы, оценку рабочих
буферов и пик RSS отдельного процесса исследования. Время решателя включает
полный проход по физическим слоям, но исключает эталон и экспорт согласно
общему протоколу. Отдельное время вызова исследования и RSS имеют более
широкую область: подготовку, эталон, прогрев и все подборочные/финальные
повторы; экспорт выполняется после снятия RSS.

RSS процесса включает библиотеки, прогрев и все повторы, поэтому небольшое
сокращение диагностических строк может быть незаметно на этом фоне. Большая
пространственная сетка, память блочной прогонки или короткая история могут
сделать `layers` практически бесполезным. Это ожидаемые ограничения,
которые итоговый отчёт должен сохранить вместе с полезными случаями.

Это зафиксированные планы для общей серии #31 после интеграции изменений,
а не уже выполненные измерения. Их можно объединить с общей матрицей
исполнителя Б до начала итогового запуска; отдельный повтор одинаковых
сценариев для #33 не требуется.
