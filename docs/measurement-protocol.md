## Метрика

Фиксируются набор узлов Q (индексы `[z,y,x]`, координаты пользователя `(x,y,z)`)
и время наблюдения. Для R независимых **полных** запусков:

`E = 100/R * sum_r(||u_r - u*||₂ / ||u*||₂)`.

Для одного узла это среднее абсолютных относительных ошибок. Для участка,
среза и поля нормы считаются по всему Q; это не среднее поточечных процентов,
не RMSE и не ошибка усреднённого решения. При `||u*||₂=0` процент равен null,
показывается средняя абсолютная L2-ошибка и `relative_not_applicable`. Отдельные
нулевые узлы внутри ненулевого Q остаются в норме. Невязка не заменяет ошибку.

Аналитическое решение — эталон итоговой ошибки. Независимое сеточное решение
служит отдельной диагностикой пространственной, временной и итерационной
ошибок. Для численного эталона без аналитики сохраняются метод и проверка
сходимости. Нельзя называть его аналитической точностью. Неполная серия не
имеет итоговой ошибки: значения успешных повторов сохраняются в исходных
данных, но их среднее не выдаётся за ошибку запрошенной серии.

## Подбор и контроль

Версия `frozen_budget_holdout_v1`. До замеров фиксируются конфигурация, Q,
эталон, цели 1/5/10%, R=5, seed, сетки и лимиты из
`benchmarks/measurement-pilot.json`. Это пилот без статистической гарантии.

1. Прогрев/JIT и построение эталона выполняются и измеряются отдельно.
2. Подбор исследует заранее заданные бюджеты на потоках `pilot`; для MC
   целевой запас 0.5 от порога, для детерминированного метода — 1.0.
   Все попытки и их полная стоимость сохраняются. Допустим существующий
   адаптивный поиск как подготовка, с исходной маркировкой своей метрики.
   Выбор для нового протокола требует пересчёта пилотной ошибки по L2.
3. До контроля сохраняется `selection.json`: выбранный бюджет, все параметры,
   критерий выбора, идентификаторы пилотных серий и seed будущего контроля.
   Отсутствие кандидата даёт `not_selected`, без фиктивной контрольной серии.
4. Новая серия `control` выполняет R полных запусков с фиксированным бюджетом.
   Её нельзя использовать для дальнейшего подбора в этой же попытке.
   Провал — окончательный результат попытки. Новая попытка имеет новый ID
   и потоки, сохраняет прежнюю и не заменяет неудачу последним успехом.

`run_seed(root, case_index, method_index, attempt_index, phase, repeat)` задаёт
потоки через NumPy SeedSequence. Индексы задаются планом, сохраняются и не
зависят от порядка запуска или Python hash. Фактический seed каждого повтора
передаётся backend и экспортируется. Для детерминированного метода seed —
записанный идентификатор повтора без влияния на ответ. R полных запусков
сохраняются и для него, чтобы сравнить разброс времени. Внутренние seed MC
проверок решателя остаются частью его конфигурации; они не заменяют holdout.

## План ранней серии и зависимости

Не запускать декартов продукт. Сначала n=16 и центр, затем n=32 и фиксированная
нецентральная точка `(1/4,1/2,3/4)`; её индексы `[3n/4,n/2,n/4]` точны
на обеих сетках. Первая таблица — обычный MC и опубликованный базовый ЛОМ,
вторая — все грани 1 рода / y0 3 рода / все грани 3 рода, beta=1 при k=1.
Для каждого случая граничные данные выводятся из одного точного решения.

Две целевые функции — `u*=1+exp(-t) sin(pi*x)sin(pi*y)sin(pi*z)` и
`u*=1+t+(x+2y+3z+xy+xz+yz+x²+y²+z²)/4` из #24. Для ранней стационарной
серии фиксируется t=0, `f=Delta(u*)` в старом соглашении `Delta u=f`.
Это самостоятельная стационарная проверка, а не выполнение временной задачи.
Опубликованные presets `sine`/`affine` не считать этими функциями без адаптера
и проверки источника и всех шести граней. До такой проверки конкретный случай
помечается `unverified`, и его нельзя выдавать за измеренный. Если готов только
один случай, публикуется он с явным пропуском второго.

Новая нелинейная временная серия (dt=.01, T=.02, alpha=0/.5, n=8 для проверки,
затем 16/32) отдельно ждёт #25/#27/#28. #26 добавляется с рабочими размерами
или ограничениями. Пакеты #29 и #32 добавляются позже при том же протоколе.
Диагностический один слой с известным прошлым полем имеет отдельный scenario;
его время не сравнивается со самостоятельным расчётом до T.

## Стоимость

`seconds` — полный запуск с нуля: подготовка F/g, оператора и грубой сетки,
все слои и итерации, переходы, остановки и обязательные проверки решателя,
включая неудачные. `preparation_seconds` — часть `seconds`, не слагаемое.
Внешнее вычисление эталонной ошибки относится к обработке измерений и имеет
отдельный таймер. JIT, независимый эталон, экспорт и визуализация исключены
из времени решателя и сохраняются отдельно. Подбор и контроль имеют отдельные
суммарные лимиты; начатый вызов может превысить мягкий лимит и не обрезается
с потерей фактической стоимости. Ресурсные ограничения backend указываются явно.

Основная таблица: среднее время полного контрольного запуска, выборочное
стандартное отклонение, максимум workspace, измеренный пик RSS и методика.
Workspace — оценка буферов, не RSS. Неизмеренный RSS — null с причиной в
metadata.memory. Пик RSS измеряется в отдельном процессе на повтор; начальный
уровень процесса записывается. Если методики ещё нет, измерение не выдумывается.
Сценарий повторного использования подготовки отделён от `cold_solve`;
амортизированная цена для M запросов: `setup/M + sum(query_costs)/M`, при
сохранении setup, M, объёма истории и реального общего времени. Не смешивать
его с полным временем одного запуска.

## Формат `measurement_v1`

Одна серия относится к одному случаю/методу/бюджету/фазе/попытке. Основной
файл `series.json` содержит metadata, reference_values, summary и trials.
`trials.csv` содержит все начатые повторы, `summary.csv` — итог одной цели.
CSV связан с JSON через `series_id`; конфигурация и окружение не теряются.
Для нескольких целей допускаются разные summaries с общим ID исходной серии.

Обязательные ключи metadata:

| Ключ | Содержание |
|---|---|
| series_id | Уникальный ID, включающий case/method/attempt/phase/budget |
| commit, dirty | Полный SHA исполняемого кода; dirty=true требует сохранённого patch/хеша |
| environment | Python, ОС, CPU, RAM, NumPy/SciPy/Numba, потоки BLAS/Numba |
| configuration | Режим, формулы/функция, n,h,dt,T,alpha, грани, backend, допуски/лимиты, scenario |
| reference | analytic/numerical, формула или метод/проверка, время наблюдения |
| query | Вид Q, points_zyx и нормированные координаты xyz, порядок значений |
| budget | Фиксированные параметры и единицы, фактические бюджеты по оценкам/истории |
| timing | Граница таймера, прогрев, эталон, подбор, обработка, экспорт; selection ID |
| memory | Метод RSS, baseline, либо причина отсутствия измерения |
| diagnostics | Невязки с нормировкой, ошибки к сеточному эталону, история отказов или пути к ним |

`Trial` хранит seed, статус/причину backend, запросные значения только при
завершении, реальное время/подготовку, память, пути на оценку (null у ЛОМ),
суммарные начатые пути/переходы, физические слои, Пикар, внутренние итерации и
completed_until. Для временного адаптера статус completed требует достижения
T по контракту #24. Для стационарного completed_until=null. При адаптивном
бюджете paths_per_estimate=null и полная история обязательна в budget/diagnostics.
Признак `stochastic` передаётся в summarize/export_series явно и записывается
в summary. Он не выводится из бюджета: при адаптивном MC с null-бюджетом
seed всех повторов тоже обязаны различаться. Для детерминированной серии
явно задаётся false; повторяющийся seed допустим.

Нормы вычисляются с предварительным масштабированием и hypot, чтобы ненулевой
эталон порядка 1e-200 не превращался в нулевой, а значения порядка 1e200
не давали промежуточное переполнение. Действительно непредставимая в float
метрика отвергается с явной ошибкой до экспорта.

Статусы итога: `confirmed`, `not_reached`, `incomplete`,
`relative_not_applicable`, `pilot_only`. Пустая или частичная серия сохраняет
затраты и причины каждого отказа; фактически не начатые повторы отсутствуют.
`seconds_to_target` заполнено только при confirmed. Причина null метрики
задаётся статусом; UI обязан показывать её текстом. Отказы unsupported и
not_selected до запуска оформляются в отдельном реестре пропусков плана.

Отношение `mean_seconds_LOM / mean_seconds_MC` публикуется только при
подтверждении обоих методов для одинаковых Q, эталона, цели и scenario.
Изменение времени самого MC при смене границ — отдельное отношение.
Проигрыши сохраняются. Графики ошибка–время строятся по сохранённым попыткам,
с различением pilot/control и версий метрики. Неполные ошибки не рисуются как ноль.

## Проверка пакета

Из этого checkout в активированном виртуальном окружении:

```sh
python -m pytest tests/test_measurement_protocol.py tests/test_heat3d_problem.py
```

Тесты используют искусственные значения для проверки формул, независимости
seed, отказов и CSV/JSON. Они не являются экспериментальными результатами.
`export_series` проверяет наличие ключей metadata и строго сериализует числа;
содержимое provenance и независимость выбора проверяет будущий runner по
сохранённым plan/selection. В этом этапе ещё нет команды реальных замеров,
графиков и пользовательского экрана: это следующие отдельно принимаемые пакеты.

## Согласование с PR #36

В #36 study_protocol.error_metrics использует ту же математическую L2-метрику,
но другой протокол fixed_candidate_independent_final_v1, фазу final вместо
control и нумерацию повторов с 1 вместо 0. До интеграции нужен явный адаптер
и единый источник численного вычисления метрики (устойчивая реализация
query_error данного пакета). Архивы нельзя объединять заменой меток:
сохраняются исходные ID протокола, фазы, запас подбора, выбранный бюджет
и происхождение финальной серии. Данная правка не изменяет чужой PR #36.
